# Delegated catalog approvers

The catalog approval gate stays in place. This local dev/setup policy is a
stopgap for Warden grants/roles/token exchange, with Gatecrasher as the future
decision UI. The declarative principal bundles can later be generated by or
replaced with Warden; this adds no identity system or signing key. Gatecrasher
integration is separate.

`catalog-approvers.json` lives beside the database selected by
`catalog.defaults.state_db`, alongside `catalog-approver.json` (operator
passphrase verifier). It is UTF-8 JSON, not a catalog bundle file. Edit it as the
operator and replace it atomically. The daemon re-reads it on each delegation
and visibility request without discarding plans or approvals. An invalid file
denies delegation; after a configured file is observed, deleting it does not
restore defaults in that process. An explicit empty `principals` object disables
all delegates. The file contains no credentials.

```json
{
  "max_window": "4h",
  "principals": {
    "msg://agent/example/helper": {
      "scopes": ["catalog.approve"],
      "privileged": false,
      "rate_limit": 10,
      "allowlist": [
        {
          "name": "create-launch",
          "paths": ["launches/*.yaml"],
          "actions": ["create"]
        }
      ]
    }
  }
}
```

Keys are exact authenticated service or agent URNs. The credential must hold
`catalog.approve`; `catalog.write`, `maintain`, and `tether.catalog` do not imply
it. Issued service tokens can request the dedicated capability through the
existing operator-controlled issuance flow. Policy alone never authenticates a
caller. Agent JWTs identify a bound session: approval resolves that session’s
logical agent through the current catalog to its configured `urn` (or its
`msg://agent/agent-mux/<logical-id>` address when no `urn` is set). Missing
sessions/catalog entries refuse approval; registry aliases do not grant it.
Remote approvals remain unavailable; scoped delegation uses the local socket. Session/device/anonymous identities cannot use delegation. Policy
`scopes` must contain exactly `catalog.approve`. Each principal has a required
`rate_limit` of 1–10000 successful approvals per rolling hour in this process;
a restart resets rate accounting. Refused requests do not consume the quota.

Each changed file must match a rule's path AND action (`create`, `modify`,
`delete`, `unchanged`). Globs use Go `path.Match`: `*` does not cross `/`, and
there is no recursive `**`. Rule names identify the matching policy in the
audit. Rules authorize whole file changes, not field-level or union-only edits;
use narrow paths/actions. Privileged approval defaults to false; setting
`privileged: true` explicitly permits it, but the caller still acknowledges the
plan's privileged changes and any running sessions. The old environment switch
`TETHER_CATALOG_DELEGATED_PRIVILEGED=1` affects only the legacy default below,
not explicit principal policies.

Without a policy file, Tachyon's existing `msg://service/tachyon` and
`msg://service/tachyon/<env>` service family retains its current catalog.write
credential compatibility and nonprivileged whole-catalog delegation. This is a
specific legacy exception, not an implication from catalog.write to
catalog.approve for other principals. There is no default rate cap for that
compatibility path. An explicit policy replaces it completely; include each
Tachyon URN and issue it catalog.approve if migrating to an explicit policy.

Delegates always refuse OperatorOnly plans, approver configuration, passphrase
state, breakglass state and `global.yaml` (which controls state roots and
operator/issuer trust). Breakglass never overrides these fences, per-principal
privilege permission, rate limits, running-session confirmation, digest binding
or the live-base check. An agent cannot approve its own agent/launch definition;
the existing session planning protection is retained. Batch approval remains
operator-only and requires the passphrase.

## Breakglass

```sh
tether catalog breakglass --principal msg://agent/example/helper --for 2h --reason 'development setup'
tether catalog breakglass end
tether catalog approvers list
tether catalog approvers show msg://agent/example/helper
```

Opening and ending require the existing local operator socket admission and a
terminal passphrase prompt. No passphrase flag is accepted. A single window
relaxes only the named principal's path/action allowlist. The principal must
already be configured. Duration must be positive and at most `max_window`,
which can lower the hard 4h cap. A second window refuses until the first ends
or expires. The daemon timer closes expired windows; every approval also checks
the absolute deadline before granting authority. Open/close/expiry produce
operator log notices; every delegated approval records principal, matched rule
(or `breakglass`), exact digest and plan ID in the catalog audit log. Do not put
secrets in the operator reason.

`catalog-breakglass.json` beside the policy holds one atomic 0600 record,
signed with the daemon's **existing active authissuer key** in a separate
signature domain. It is not a bearer token and has no generic signing endpoint.
A restart accepts only an unexpired signature bound to the same policy and
operator passphrase verifier. Issuer key rotation or pruning, passphrase
rotation, policy changes, bad parsing/signatures, backward clock movement or
invalid bounds close delegation. Failure remains latched until an operator
explicitly ends the invalid window with the passphrase. A denial-only
`catalog-breakglass.json.blocked` marker persists invalidation across restart,
including when signing a closure fails. It grants no authority and needs no
key. Operator end persists signed closure before removing this marker. Replacing a window does
not extend one implicitly. Restarts never restore plan approvals.

As with existing catalog and issuer trust, direct access to rewrite trusted
state/key files is outside the approval gate's threat boundary. Normal API
callers receive no key, verifier or passphrase material. The visibility commands
are read-only views; deadline cleanup and audit still run when observing state.
