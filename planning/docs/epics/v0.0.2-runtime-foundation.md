# Epic v0.0.2: Runtime Foundation

**Status:** active
**Goal:** Turn the v0.0.1 launcher into a durable local runtime. Introduce a long-lived daemon that owns active sessions, live attach/detach with input injection, the storage shape that separates durable logical agents from ephemeral runtime sessions, checkpoint and broker skeletons, a stable local API transport, and an internal event bus. Preserve the v0.0.1 CLI path while opening the door to non-CLI clients.
**Theme:** Durable local runtime with attach/detach, checkpoint/handoff skeletons, brokered messaging, stable client API.
**Dependencies:** v0.0.1 Foundation (shipped)
**Exit criteria:**
- [ ] A long-lived `mux` daemon (either `cmd/muxd` or `mux daemon`) owns running sessions across invocations; `mux sessions list` from a fresh process shows sessions the daemon owns.
- [ ] `mux sessions attach <id>` produces a live tail-follow stream; multiple clients can attach simultaneously; detaching does not kill the session.
- [ ] `mux sessions input <id>` (or API equivalent) delivers bytes to the running PTY.
- [ ] `logical_agents`, `checkpoints`, `broker_envelopes`, `events`, `client_attachments` tables exist; `sessions` references `logical_agent_id`; a migration framework is in place.
- [ ] Provider interface supports both CLI (PTY) and API (streaming SDK) runtimes; env handling merges passthrough + overrides onto inherited base (not blind replacement).
- [ ] A local HTTP (or Unix socket) API exposes session lifecycle + attach stream + checkpoint + broker endpoints per context-pack §08.
- [ ] `internal/events` pub/sub bus publishes session-lifecycle and broker events; persists to the `events` table; is exposed via `GET /events/stream`.
- [ ] Repo has lint / staticcheck / govulncheck / gotestsum targets, CI-friendly Make targets, package READMEs, and an ADR folder.
- [ ] All v0.0.1 CLI commands still pass the smoke path.

## Motivation

Context-pack §00 states the v0.0.2 deliverable target is "the minimal irreversible foundation." Context-pack §06 enumerates the specific limitations of v0.0.1: one-shot runtime, snapshot-only attach, aggressive env handling, and unsynchronized state. Context-pack §02 introduces the entity model (LogicalAgent / RuntimeSession / Checkpoint / BrokerEnvelope) that must be reflected in storage before any integration work. Context-pack §08 sketches the local API shape that Nanite and Clockwork need to exist before they can become clients.

The architectural payoff: after v0.0.2, the daemon is the single owner of runtime truth, and every other surface (CLI, TUI, Nanite, Clockwork, future MCP/GUI) is a client of the same local API. The entity model is durable. The provider layer is runtime-mode agnostic. Each subsequent version can add features without re-shaping the foundation.

## Scope

### In
- Daemon/runtime entrypoint with lifecycle commands (start/stop/status).
- Live attach (tail-follow) + SendInput + multi-client attach semantics.
- Storage evolution: new tables + migration framework + LogicalAgent split.
- Provider contract evolution: CLI and API runtime modes share one session model; env-merge fix.
- Local API transport (HTTP, optionally Unix socket) exposing lifecycle/attach/checkpoint/broker/events.
- Event bus (`internal/events`) with pub/sub + persistence + SSE subscription.
- Repo hygiene: lint/staticcheck/govulncheck/gotestsum, Makefile targets, ADR folder, package READMEs.

### Out (deferred to v0.0.3+)
- Nanite/Clockwork adopting the local API (v0.0.3).
- First concrete API-backed provider implementation (v0.0.3).
- Checkpoint-resume end-to-end path (v0.0.3).
- Request/reply semantics on broker envelopes (v0.0.3).
- Hot/cold policy, memory scopes, operational agents (v0.1).
- Rich TUI/GUI, desktop, full Cerberus integration (v0.3+).

## Review / readiness notes

- **Daemon transport choice:** HTTP vs Unix socket vs both. Lean HTTP on loopback for v0.0.2 (simpler client story for Nanite/Clockwork later) with a Unix-socket option behind a flag. Confirm before Sprint v002-05 starts.
- **Migration framework pick:** embedded `.sql` files + hand-rolled migrator vs `golang-migrate` vs `goose`. Context pack says "use migrations" without prescribing. Decide as part of Sprint v002-03's first task; capture as an ADR.
- **Provider API-mode concrete implementation:** Sprint v002-04 leaves the API provider as an *interface and scaffold*. The first real API-backed provider is v0.0.3 work to keep v0.0.2 scoped. If readiness review wants a smoke implementation in v0.0.2, add a task there rather than smearing into other sprints.
- **Checkpoint/broker skeletons in v0.0.2 are skeletons only.** They introduce tables, types, and API endpoints that return/accept well-formed payloads, but full resume and request/reply semantics land in v0.0.3. Sprint v002-03 and v002-05 both need to respect this line.
- **LogicalAgent seeding:** existing `agent_id` strings in the v0.0.1 catalog are YAML IDs; the new `logical_agents` table needs a seeding path so the existing demo launch still works. Sprint v002-03's first task must address this explicitly.
