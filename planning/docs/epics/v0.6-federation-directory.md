# Epic v0.6: Federation Directory

**Status:** next
**Goal:** A first-class directory service in Mux that holds thin, publicly-discoverable identity profiles for every federating entity — agents and projects in v0.6; later skills, MCP servers, and remote mux instances — under one URN namespace. Owning substrates keep operational truth in their own stores; the directory holds identity + a callback back to the ops store. This becomes the federation pattern for anything that participates through Mux.
**Theme:** One discovery surface, many owners. Clean identity ↔ ops separation.
**Dependencies:** v0.0.5 (MCP + Provider Integration) — uses the muxd HTTP/MCP surface and SQLite store.

**Exit criteria:**
- [ ] Two-store model documented and enforced: Mux registry holds public identity; owning substrate holds operational config; `urn` is the join key.
- [ ] Mux-minted opaque IDs live for `agent` and `project` kinds: `agt_<10alnum>` / `prj_<10alnum>`, returned on register, immutable.
- [ ] Federation directory schema shipped behind a versioned migration with a `mux_instance_id` column reserved (default `'agent-mux'`) for future multi-mux federation.
- [ ] CRUD operations (Register, Lookup, Search, UpdateSelf, Deregister, Sync) exposed at parity across HTTP (`/registry/{kind}`), MCP (`tether_registry_*`), and CLI (`mux registry ...`).
- [ ] Bootstrap importer auto-imports the existing `~/.tether/catalog/{projects,agents}/*.yaml` population on first daemon start, idempotent on re-run, with `callback = file://<path>` recorded so consumers can `Sync` to refresh.
- [ ] `file://` and `cli://` callback resolvers live; `http://` and `mcp://` deferred to Sprint v060-02.
- [ ] Cross-substrate consumer (agridd) integrated via the Client interface; FU-31 / CW-20260520-0046 unblocked.
- [ ] ADR captures the directory model, two-store separation, and the deliberate distinction from the v0.2 "no installer registry" constraint.

## Motivation

Agents and projects are launching more regularly. There is no single place to ask "who exists, what can they do, how do I reach them" across the fleet. Each substrate (Tether's launch catalog, agridd's `agent_profiles`, future substrates) currently holds its own local view. There is no shared directory, no shared addressing, and no way for one substrate's agent to discover or message another substrate's agent through Mux.

This epic creates that directory. It is deliberately a **directory service**, not an installer-registry: Mux holds publicly-discoverable identity (display name, role, capabilities, skills, links, avatar, status) and points back to whoever owns the operational config. Substrates retain ownership of their ops data; Mux owns discovery and addressing.

Cross-substrate alignment for this work was completed in-band over mux messaging on 2026-05-20 between `msg://agent/agent-mux/tether-registry-design` and `msg://agent/agent-mux/agridd-keeper` (see CW-20260520-0046). Schema, ownership, interface contract, and dual-maintenance model (push via `UpdateSelf` or pull via `callback`) are all locked before any code lands.

### Relationship to v0.2 — Agent Definition + Asset Resolution

v0.2's epic file says "Agent Mux does not own any installer, registry, or catalog logic." That statement refers to **installer-registry** (package install/uninstall/update flows owned by Agent Ops). v0.6 does **not** contradict it: v0.6 is a **directory** of who-exists, not an installer of what-to-install. Substrate-owned operational config (provider, prompts, allowed tools, permissions, repo paths) stays in the substrate that owns it; Mux only holds the identity-side projection.

### Relationship to existing `internal/registry`

Tether already has a package called `internal/registry` — that is the **launch-resolution layer** over `~/.tether/catalog/*` (ingests YAML into a `FileBackedRegistrar` for the launch path). It is read-only and serves a different concern. The v0.6 directory service is a separate package. Naming and package-layout are resolved as a sub-decision in v060-01 Task 1.

## Scope

### In
- `agent` and `project` kind rows with the thin-profile schema (urn, display_name, title, role, description, capabilities[], skills[{name, learned_at, level?, via?}], links[{kind, target}], avatar, project, status, last_updated_*).
- Mux-minted opaque IDs (`agt_<10alnum>`, `prj_<10alnum>`).
- `kind_meta` JSON column for kind-specific identity extras (not ops config).
- Optional `callback` URI back to the ops store, with `file://` + `cli://` resolvers.
- Optional `cached_payload` + `cached_at` for the last callback response.
- `mux_instance_id` reserved column (default `'agent-mux'`) for future multi-mux federation.
- CRUD ops at full HTTP / MCP / CLI parity.
- Bootstrap importer for Tether's existing catalog YAML population.
- Soft-delete via `status = 'deprecated'`. No hard delete v1.
- ADR documenting the model.

### Out (deferred)
- `http://` and `mcp://` callback resolvers — Sprint v060-02.
- Multi-mux instance federation (cross-host UpdateSelf, per-agent token auth) — Sprint v060-02+.
- Additional kinds (`skill`, `mcp_server`, cerberus's `service` / `resource` / `domain` / `container` / `connector`, formal `secret`) — Sprint v060-03.
- Sysop UI surface for browsing the registry — separate sprint, post-Sprint 1.
- Capability-similarity / fuzzy search ranking — defer until concrete UX demands it.
- Hard delete / GDPR-style purge — separate sprint when needed.
- Backfilling existing Tether catalog YAMLs with their newly-minted `urn` — Sprint v060-02 (decided as a follow-up; out of scope here to keep Sprint 1 read-only against ops stores).
- Cerberus catalog bootstrap import — Sprint v060-02, paired with the cross-substrate dedup primitive (`LookupBy(kind, external_id, substrate?)`) that prevents double-registration of projects both substrates own files for.

## Candidate sprints

- **v060-01 — Registry Foundation** (10 days). Schema migration, storage, service core, file:// + cli:// callbacks, HTTP/MCP/CLI surfaces, bootstrap importer, ADR. Ships the full surface for `agent` + `project` kinds. agridd's Phase 3 Stage 3.d.2 gated on this.
- **v060-02 — Cross-Substrate Bootstrap + Dedup** (drafted, see [sprint file](../sprints/v060-02-cross-substrate-bootstrap-dedup.md)). Cerberus catalog auto-import (reads `~/.cerberus/registry.yaml` as the source-of-truth index), `LookupBy(kind, external_id, substrate?)` dedup primitive in a sibling `registry_external_ids` table, URN write-back to source YAMLs (Tether + cerberus both get `registry_urn:` lines), merge admin command for residual duplicates. Closes the cerberus follow-ups identified during v060-01 coordination.
- **v060-03 — Federation Transport** (TBD). `http://` and `mcp://` callback resolvers, mux-instance-aware lookup helpers (using the `mux_instance_id` column reserved in v060-01), ADR for cross-host token model. Enables federation beyond same-host UDS trust.
- **v060-04 — Additional Kinds** (TBD). cerberus kinds: `service` (svc_), `resource` (res_), `domain` (dom_), `container` (ctr_), `connector` (con_); `skill` (skl_) and `mcp_server` (mcp_) kinds; formal `secret` (sec_) kind paired with cerberus's 1Password mechanism (CW-20260519-0027); sysop registry browser UI.
- **v060-05 — Group Messaging** (drafted, see [sprint file](../sprints/v060-05-group-messaging.md)). New `group` registry kind with URN path variant `msg://group/<grp_id>`; group-mailbox messaging (per-member read cursor, mentions, archive) for multi-agent coordination rooms. Introduces the `@` (daemon-parsed mention) / `!` (agent-side action) / `:` (agent-side directive, dispatches to the directives package) symbol vocabulary. Runs in parallel with v060-03/04 after v060-01 ships.

The `:` lane (inline directives) is owned by the consuming chat-engine, not Tether — `agridd` implements first (FU-35), `nanite` ports the pattern. Tether's responsibility is the namespace reservation in v060-05; no Tether-side sprint needed.

## Review / readiness notes

- **Cross-substrate coordination is CLOSED.** Schema, ownership, six-question Q&A, and the two-store model were resolved before sprint authoring. Do not reopen those decisions in sprint planning. If a substantive design question surfaces during implementation, ping `msg://agent/agent-mux/agridd-keeper` rather than freelancing.
- **The launch-resolution layer (`internal/registry/`) is unrelated.** Do not modify it as part of this epic. Sprint v060-01 Task 1 resolves the package-name layout.
- **Tether's existing 22 projects + 8 agents** are auto-imported on first daemon start. agridd's Client uses `LookupOrRegister(urn, profile)` to avoid double-registering them.
- **`kind_meta` discipline.** Operational config (provider_overrides, system_prompt, agent_prompt, permissions, knowledge_base, repo_root) stays in the source YAML / substrate store; it does **not** belong in `kind_meta`. `kind_meta` is for kind-specific identity bits that don't fit the unified columns (e.g. project: human-friendly repo/tracking paths for display; agent: secondary roles[] beyond the primary `role` field).
- **Same-host UDS trust model.** No per-agent auth v1. If agridd or another substrate later needs cross-host UpdateSelf, that lands in Sprint v060-02 with its own ADR.
- **Federation language.** User-facing surfaces use "registry" everywhere (HTTP path, MCP tools, CLI subcommand, ADR title) since that is the term agridd-keeper, chrispian, and the literature use. Internal Go package naming is a sprint-level decision.
