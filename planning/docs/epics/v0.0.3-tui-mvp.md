# Epic v0.0.3: TUI MVP

**Status:** next
**Goal:** Deliver a keyboard-driven terminal UI that fronts every day-to-day interaction with Agent Mux through a single elegant surface. The TUI lets a user search across every catalog object, inspect and edit any of them, manage running sessions, and launch sessions either from saved profiles or through a short wizard. It is a parallel track that runs alongside Nanite integration: Nanite is the chat UX client; this TUI is the runtime/ops UX client. Both consume the same v0.0.2 local API.
**Theme:** TUI MVP — universal search, keyboard-first CRUD, session management, launch wizard, command palette; consumes v0.0.2's local API.
**Dependencies:** v0.0.2 Runtime Foundation, specifically Sprint v002-05 (Local API). Sprint 3 of this epic additionally depends on a catalog-CRUD API decision (see readiness notes).
**Exit criteria:**
- [ ] A `mux tui` subcommand runs a Bubble Tea program that speaks to the daemon over the v0.0.2 local API transport. With the daemon up, it becomes the primary interactive surface for Agent Mux.
- [ ] Main screen is a single keyboard-driven panel: fixed search input on top, fixed filter chips row below it, scrollable mixed-type results area, fixed footer showing current-screen keybindings.
- [ ] Full CRUD for every user-listed catalog object: projects, agents, providers, launches.
- [ ] v0.0.2-era runtime objects — LogicalAgent, Checkpoint, BrokerEnvelope — have list / inspect / create / edit / resume-or-reply surfaces in the TUI.
- [ ] Session management: list, attach live via SSE, send input, stop, tail-log snapshot.
- [ ] Two launch flows: (a) quick-launch from a saved launch profile (Enter on a launch row), (b) multi-step wizard (project → agent → provider → options → review; exit as ephemeral launch / save-and-launch / save-only).
- [ ] Command palette reachable via `:` or Ctrl-K; fuzzy-matches navigation verbs (`view projects`, `add launch`, `resume checkpoint`, `show events`, etc.).
- [ ] `?` help overlay enumerates the current screen's keybindings.
- [ ] Lipgloss theme is cohesive — one dark default, one alternate (e.g. high-contrast) — with consistent borders, padding, and accent color.
- [ ] TUI behaves sanely when the daemon is down: clear error with a suggestion to run `mux daemon start`; no fallback into in-process mode.

## Motivation

Agent Mux today is a CLI-only runtime. The CLI is fine for scripted invocation but it's friction-heavy for the thing users actually do most often: pick a launch profile and run it, inspect a running session, fix a typo in a YAML and re-launch. Context-pack §03 catalogues this as v0.3+ "rich UX," but user feedback and the v0.0.1 dogfooding story argue for pulling a focused TUI forward: users need an elegant daily-driver surface before the more speculative v0.1 / v0.2 themes land.

This epic pulls a scoped subset of that v0.3+ theme forward. It is deliberately narrow — keyboard-only, single binary, single transport — so it can ship without blocking the (now-parked) Nanite/Clockwork Integration Foundation and without re-opening the v0.0.2 runtime contract. The TUI is a *client* of the v0.0.2 daemon API, following the same rule the rest of the architecture follows: "The UI is always a client of the runtime, never the source of runtime truth" (context-pack §01).

The architectural payoff: after this epic, the daemon API has two real in-tree clients (the thin CLI client from v0.0.2 Sprint 1 and this TUI). Any gap in the API surface — especially around catalog CRUD and ephemeral launches — gets surfaced by the TUI's consumption pattern and either feeds back into v0.0.2 (if caught early) or into a follow-up release. Every consumer of the API after this — Nanite, Clockwork, an eventual desktop GUI — benefits from the shakeout.

## Scope

### In
- `mux tui` subcommand under `cmd/mux/` launching a Bubble Tea program.
- Main screen with Lipgloss layout: search input, filter chips, mixed-type results viewport, footer keybindings hint.
- Client package (`internal/tui/client/`) that wraps the v0.0.2 daemon API — list/get/create/update/delete for catalog objects; session lifecycle; attach SSE subscription; input POST; event stream subscription; broker envelope and checkpoint endpoints.
- CRUD screens (list + form) for Project, Agent, Provider, Launch.
- CRUD / inspect screens for LogicalAgent, Checkpoint, BrokerEnvelope.
- Session list, live attach panel (SSE stream + input line), stop + tail actions.
- Quick-launch (Enter on a launch row) and full wizard (project → agent → provider → options → review; ephemeral / save-and-launch / save-only).
- Command palette overlay (`:` / Ctrl-K) with fuzzy-matched verb registry.
- `?` help overlay per screen.
- Two Lipgloss themes.
- Toasts / non-blocking notifications.
- First-run onboarding hint when the catalog is empty.
- TUI keybinding reference doc under `docs/tui-keybindings.md`.

### Out (deferred to v0.3+ or later)
- Mouse support. Keyboard-only in v0.0.3.
- Web UI / desktop GUI.
- Workflow visualization (swimlanes, handoff timelines, multi-session broker flows). Context-pack §04 multiplexor pattern stays a v0.3+ concern.
- Remote-daemon support. Local transport only.
- Two-client concurrent edit conflict resolution (see readiness notes).
- Wizard draft persistence across TUI restarts (see readiness notes).
- Plugin / extension model for screen types.
- Theming customization beyond the built-in themes.
- Cerberus supervision of the TUI process — not applicable; the TUI is a user-foreground process.

## Decisions already locked

- **D1 — Stack.** Bubble Tea + Bubbles + Lipgloss. Use Bubbles' `list`, `textinput`, `textarea`, `viewport`, `paginator`, and `spinner` primitives rather than hand-rolling. This is a small-surface idiomatic Go TUI stack and matches the "small UI footprint but looks excellent" target.
- **D2 — Transport.** Target the v0.0.2 daemon local API. Do NOT embed `app.Service` in-process. The TUI is a daemon client like everything else.
- **D3 — Keyboard-only for v0.0.3.** Mouse support is deferred to v0.3+. Every feature must be reachable from a key.
- **D4 — Themes.** One primary dark theme. One alternate theme (likely high-contrast). Both ship in Sprint 6. Do not bikeshed theming before basics work.
- **D5 — Single binary.** Add a `mux tui` subcommand under `cmd/mux/`. Do NOT create a separate `cmd/muxtui/` entrypoint unless Sprint 1 readiness review surfaces a concrete reason (binary-size bloat, independent release cadence, cross-compilation differences).
- **D6 — Ephemeral launches are first-class.** A user does not need to save a launch YAML first. The wizard's review step exposes launch-only as an explicit option. This requires daemon support for an ephemeral-launch request shape; flag as readiness gap if v0.0.2 Sprint 5 doesn't expose it.
- **D7 — Daemon-only.** If the daemon is down, the TUI shows a friendly error and suggests `mux daemon start`. It does not fall back to an in-process service. This keeps "daemon owns runtime truth" unambiguous.

## Review / readiness notes

- **Catalog CRUD API dependency.** v0.0.2 Sprint 5 defines session / checkpoint / broker endpoints but NOT catalog CRUD (projects / agents / providers / launches). Before Sprint v003-03 runs, one of three paths must be chosen and recorded in an ADR: (a) v0.0.2 Sprint 5 gains a catalog-CRUD task retroactively; (b) the TUI writes YAML directly to the catalog root and triggers a daemon reload via a dedicated endpoint (e.g. `POST /catalog/reload`); (c) a new parallel v0.0.2 Sprint 8 "catalog API" is added to v0.0.2's backlog. The trade-off: (a) is cleanest but expands v0.0.2 scope; (b) matches the existing "YAML is truth" shape but forces two clients (CLI + TUI) to duplicate file-format logic; (c) is cleanest architecturally but gates this epic on another v0.0.2 sprint landing. Sprint v003-03 is blocked on this decision.
- **Ephemeral-launch endpoint.** D6 locks ephemeral launches as first-class, but v0.0.2 Sprint 5's `POST /sessions` shape accepts `launch_id` and leaves "inline plan" as an unspecified option. Before Sprint v003-04 runs, confirm the daemon accepts an inline plan payload (project/agent/provider/options with no `launch_id`), or add a task to v0.0.2 Sprint 5 to extend the endpoint. Otherwise the wizard's "launch-only" exit silently can't work.
- **SSE vs WebSocket for live attach.** Sprint v002-05 leans SSE. If that decision holds, the TUI's attach panel uses `r3labs/sse` or `net/http` with a line-buffered reader. If it flips to WebSocket, swap the client library. Decide before Sprint v003-02.
- **Config-write conflict handling.** Two clients (CLI doing `mux agents edit`, TUI doing the same via the form) could race on the same YAML. v0.0.3 does not address this — last-write-wins on disk. Document the limitation. Revisit in a later version (likely when the catalog-API decision lands).
- **Wizard state persistence across restarts.** An in-progress wizard draft is held in TUI memory only. If the user quits, draft is lost. Deferred. If user feedback shows it hurts, revisit in v0.0.5+ with a `~/.agent-mux/tui/drafts/` directory.
- **Terminal compatibility.** Minimum terminal size and color-depth fallback (ANSI-16 vs 256-color vs truecolor) are Sprint v003-06 concerns. Capture now so Sprint 1's theming work doesn't over-commit.
- **Keybinding collisions.** The wizard's `s` (save-and-launch) and the list-view `s` (save) are not the same verb and need a consistent convention. Sprint v003-06 does a full audit. Capture per-task collisions as readiness gaps as they're noticed earlier.
- **Sprint sequencing.** Sprints 1 → 2 → (3 ‖ 4 ‖ 5) → 6. Sprints 3, 4, and 5 can run in parallel once the screen-stack and form-framework foundations are in place. Sprint 6 is the final polish pass and depends on everything else landing.
