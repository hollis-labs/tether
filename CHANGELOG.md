# Changelog

All notable changes to Tether are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Pre-1.0: minor bumps for additive surface, patch bumps for fixes — breaking changes can land in any minor.

This file was backfilled from the git history and is a good-faith summary, not an exhaustive one; `git log` is the complete record. Entries are grouped by tagged release. Consumers should watch this file for new HTTP routes, MCP tools, CLI commands and catalog/configuration changes.

## [Unreleased]

Changes on `main` since v0.6.0.

### Added

- **An MCP server catalog entry can take a credential from a private file.** (CW-20261001-0229) `file:///abs/path` or `file://~/path` in `args:`, `env:`, `token:` or `url:` is read at spawn time, so the catalog YAML no longer has to carry the secret. The file must be a regular file owned by the current user with mode 0600 or tighter (a group- or world-readable file is refused), and a symlink must stay inside the catalog directory or the operator's home. A missing, empty or oversized file, or one that is not a regular file (a FIFO is refused before it is opened, so it cannot hang the load), fails the load with an error that names the file and never contains its contents. The value is redacted from an upstream's stderr tail, tool-call errors, launch records and the connect errors in a server's status and the log, like a keychain value, and a `url:` that came from a reference is scrubbed too. Only a `file://` the catalog YAML wrote is a reference: a value that becomes `file://` through `${VAR}` stays a literal, and `${VAR}` is not expanded inside a `file://` path (`~` still follows `$HOME`, which a launch's environment can set, so use an absolute path to pin the file). Put the reference in `env:` to keep it off the command line; in `args:` the value is still on the upstream's `/proc/<pid>/cmdline`, and `tesseract mcp` and `hadrond mcp` currently take their token only as `--token`. A literal MCP-entry value written as `file://` is read as a credential file, so one that is not fails the load; none exists in the live catalog. See `docs/secrets.md`.
- **Opt-in retention for the `events` table.** `daemon.events_retention` in `global.yaml` (`enabled`, default `false`; `days`, default 90, where 0 or negative turns it off) runs an hourly sweep. The sweep deletes events older than the window, by age only, in bounded batches, and logs how many it removed. Off by default, so upgrading deletes nothing; replay within the window is unchanged. The daemon's wake sweep and this sweep now share one periodic-job loop. (CW-20260930-0008)
- **Idempotent session create and resume.** `POST /sessions` and `POST /logical-agents/{id}/resume` accept an optional `idempotency_key`: a retry with the same key and request returns the session the first one created (`replayed: true`, HTTP 200), and the same key with a different request answers 409 `idempotency_conflict`. Launching a keyed session again is idempotent too. Keys are global and unauthenticated, so prefix them. Surfaced in the Go client (`ResumeLogicalAgentWithOptions`), the MCP `mux_session_create` / `mux_logical_agent_resume` tools, and `mux launch --idempotency-key` (CW-20260930-0229).
- **Messaging surfaces.** Scoped role/slot binding across CLI, MCP, HTTP and the Go client; a durable participant registry with canonical sessions and leased runtime bindings; durable hosted-session handoff with route fencing; delivery trace, operator repair and privacy-safe retention; and a bounded, server-only inbound A2A relay adapter.
- **MCP adapter: streamable-HTTP transport**, so an upstream restart no longer severs connected agents. Upstream `sse`/`http` connections and supervision now use the shared `go-mcp` client and supervisor packages.
- **Registry: derived/authored field split on project entries**, callback-backed derivation, an onboarding/lookup surface, flat authored `props`, and minter/owner provenance with symmetric redaction on write routes.
- **Launch profiles.** `config.Agent` is now `LaunchProfile`, with compositional launch resolution and a Global > Project > User settings cascade for onboarding configuration.
- **Runtimes.** An `opencode` runtime on the structured go-providers adapter (with resume verification and a skills compiler) and an Antigravity (`agy`) runtime with detect/seed/doctor support and provider events.
- **MCP proxy:** typed identifier extraction from proxied calls into session refs, and bounded workstream provenance on forwarded calls.

### Changed

- **Library bump: go-agent-wrapper v0.25.6, agentkit v0.21.0, go-providers v0.42.0, go-sandbox v0.6.0, go-runner v0.8.2, go-llm-contracts v0.4.0** (go-llm-types stays at v0.5.1). (CW-20261001-0210) Every first-turn argv, and every other runtime's argv, is byte-identical to before, because Tether launches through the prepared launch template and agentkit v0.21.0 changes only the path without one. The one argv that changes is a codex exec turn that resumes a thread, which gains `resume <id>` (first bullet below). What changes, as measured on a live daemon with the real codex-cli 0.159.3:
  - **A codex exec session resumes its thread from turn 2.** Within one session, turn 2 runs `exec … --cd <project> resume <id> -- <prompt>`, with every exec option in front of `resume`, in the same `CODEX_HOME`, and both turns end up in one codex thread (one rollout file holding both prompts). Before, every turn started a new thread.
  - **A logical-agent resume of a codex agent starts a fresh thread.** It is a new session with a new boot dir and so a new `CODEX_HOME`, and the checkpoint Tether writes carries no provider session id (`provider_hints_json` is empty), so the first turn has no `resume`; that session then resumes its own thread from its second turn. Nothing carries a codex thread across boots.
  - **If a checkpoint's provider hints ever do carry a thread id,** resuming into a `CODEX_HOME` that lacks it fails that one turn as a provider session loss, not as a launch failure and not as a 502: the turn returns `provider_session_lost` (HTTP 409), the session log records `[session_lost] requested=<id>` and codex's own `no rollout found for thread id` line, and the next turn starts a fresh thread. Nothing in Tether writes such hints today. No `provider.session_lost` event is published for this case: the lib reports it through the session log marker, and Tether's event covers a turn that ran on in a new session.
  - A per-turn resume that fails because the provider no longer has the session now leaves a `[session_lost]` marker in the subprocess session log, for an adapter that classifies the loss (agentkit v0.20.2). Measured here for codex exec; I did not exercise the Claude or OpenCode adapters.
- **The `mux mcp` server Tether plants in each agent no longer opens the state database.** It runs inside the agent's sandbox and used to open `tether.db` read-write in-process (migrations, the logical-agent seed, and the proxy's tool-call events), which is why the state directory could not be protected. Launched sessions now get `mux mcp --daemon-only`: it reads and writes Tether state only through the daemon's API, the daemon records each tool call itself, and it refuses to start without a reachable daemon (`tether daemon unreachable; mux tools unavailable`). An agent launched while `muxd` is down has no mux tools. An operator's own `mux mcp` and `mux boot-exec` are unchanged. (CW-20261001-0173)
  - **Client-visible:** `POST /proxy/events` accepts optional `phase` (`start` or `end`) and `publish`. With `publish` the daemon publishes the call on its event bus, and a non-empty `session_id` must name an existing session (400 otherwise). It checks shape and size (400 on a malformed record or a body over 64 KiB; an over-long `error` is cut to 4 KiB with a `…[truncated]` marker). **For every caller, published or not, the daemon now stamps the time itself and ignores `timestamp`.** `GET /sessions/{id}` gains `workstream_id`.
  - **Inside an agent**, `mux_session_health` and `attached_clients` now come from the daemon (before, the planted server asked its own empty session manager), and `mux_logical_agent_list` returns the daemon's summary rather than the table row, with different JSON keys (`id`, `name`, … rather than `ID`, `Role`, …). An agent launched while `muxd` is down has no proxied upstream tools either, not only no native tools.
- **Permission modes reach each provider as a posture, with no change to what an agent may do.** go-agent-wrapper v0.23.0 (agentkit v0.19.1, go-providers v0.39.0, go-sandbox v0.5.1) takes a launch's permission as a go-permission posture and refuses a provider's own spelling. Tether now maps `permission_mode` onto one posture per provider, the same in both launch engines:
  - claude: `bypass` runs with `--permission-mode bypassPermissions` instead of `--dangerously-skip-permissions`, and `default` runs with `--permission-mode default`.
  - codex: runs `workspace-write` with `approval_policy` `on-request` in both modes, as before. That is the policy under which its MCP tool calls are asked for and approved, rather than refused.
  - opencode: keeps its own defaults.
  - antigravity: `bypass` passes `--dangerously-skip-permissions`, and `default` passes `--mode accept-edits`.

  (CW-20261001-0156)
- **Client-visible: ACP launches (Copilot, Pi) are on.** The `TETHER_ENABLE_ACP` gate and its 403 `forbidden` answer are gone. The gate guarded against a go-agent-wrapper panic that took the daemon down when an ACP agent exited during launch, which v0.21.1 fixed. A launch whose agent exits early now fails like any other launch. The ACP runtime's `[permission_denied:…]`, `[auth_failed]` and `[session_lost]` log markers take the format the native runtimes write. (CW-20261001-0156)
- **Security: on Linux, Claude and OpenCode agents can no longer write Tether's catalog, run directory or state directory; Codex is not protected.** Every agent the daemon launches, except Codex, runs with the catalog root, the daemon's run directory (`muxd.pid`, `muxd.sock`) and the directory holding the state database as read-only protected paths, registered by real path. The paths are added to the agent's sandbox profile when it has one; otherwise a minimal profile applies whose only effect is the protection. The daemon still writes all three. The state directory joined once the `mux mcp` server planted in each agent stopped opening the database (CW-20261001-0173): it now runs `--daemon-only`. A `mux` command an agent runs by hand that opens the database itself (`mux resolve`, `mux projects list`, `mux acp`, `mux workspaces prune`, and the migrations check of `mux doctor`) fails inside the sandbox with `attempt to write a readonly database`, or `unable to open database file` when the daemon is down (CW-20261001-0470); the `mux_catalog_list_*` and `mux_health` tools do the same job through the daemon. The state database stays readable by every agent (CW-20261001-0263). Because its directory is protected wherever it is, a `defaults.state_db` in a shared directory (`$HOME`, `/tmp`, `/`) makes that whole directory read-only for every wrapped agent: give the state database its own directory.
  - **Codex is NOT protected by this.** Tether does not wrap Codex: its `workspace-write` sandbox is bubblewrap too and cannot nest inside Tether's where unprivileged user namespaces are restricted, so wrapping it would stop it running shell commands. Codex runs exactly as it did before, under its own sandbox, which makes the catalog, run directory and state directory read-only to its shell (unless `state_db` is in a directory that sandbox can write: `/tmp`, `$TMPDIR` or the work directory). But Codex spawns every MCP server it is given outside that sandbox, so a Codex agent can reach the catalog through MCP tools: `torque_session_launch` with a caller-chosen `workdir` (CW-20261001-0464; inferred from the real tool, not demonstrated end to end), `loom_export_bundle(dir=…)` writing into an arbitrary directory (CW-20261001-0465; reproduced), and the `nanite` and `cerberus` host shells if granted. The default `torque`/`tesseract` allow-list is not safe for Codex either. **The structural fix is MCP upstreams that run daemon-side (CW-20261001-0230).** Until then `GET /health` (`sandbox_protect.codex`), `mux doctor` (a new `sandbox-protect-codex` warning) and the daemon's startup log say `codex: not protected (CW-20261001-0230)`. Claude, OpenCode and every other agent Tether wraps stay protected. Earlier revisions of this change called Codex guarded, under an allowlist of its flags, environment, injection, project config and MCP list re-checked before every turn; three adversarial reviews found that could not be made sound, and the claim is withdrawn. The guard stays in the tree, dormant behind one switch (`codexProtectionMode`), with what it would need written down in docs/sandboxing.md.
  - **Operator-visible:** where bubblewrap is missing or cannot build a namespace, a launch Tether must sandbox is refused with an install hint. `TETHER_SANDBOX_PROTECT=0` (or `false`) in muxd's environment turns protection off; the daemon then logs a WARN line at startup. `mux doctor` has a new `sandbox-protect` check that asks the running daemon, warns when protection is off, and fails when it is on but bubblewrap cannot build a namespace; `GET /health` gains `sandbox_protect`, with `codex` and `codex_reason`. On macOS protection is not applied until go-sandbox's seatbelt protection is verified on a real Mac (CW-20261001-0138). An agent under the minimal profile sees a private PID namespace, loses background processes when a per-turn CLI's turn ends, finds `/home`, `~` and `~/.tether` as separate mounts (`rename` across them fails with `EXDEV`), and cannot use `sudo`.
  - **Operator notes:** a session already running keeps the MCP configuration planted when it was launched until it is relaunched or resumed, and a session planned before this change carries no record of which environment keys came from a caller (`caller_env`), so its plan counts as having none (nothing reads it while Codex is unprotected).
  - **Client-visible:** while protection is on, these launches are refused with 403 `forbidden`: a launch (not Codex's, which is not protected) whose work directory, project root or workspace lies inside a protected directory, the state directory included; a launch Tether must sandbox on a host where it cannot; and every ACP launch (Copilot, Pi), until go-agent-wrapper can protect one without a sandbox policy (CW-20261001-0162). From inside an agent, `mux_agent_create` and `mux_agent_edit` that would write under the catalog, run directory or state directory return a typed `catalog_read_only` error. That is a policy of the planted `mux mcp` (started with the new `--protect-path <dir>`), enforced for every runtime, Codex included, not an effect of a read-only mount, which exists only inside Tether's sandbox: Codex spawns MCP servers itself, outside it, and a Codex agent could otherwise write the catalog through `mux_agent_create scope=system`. It holds against a symlink re-pointed while the call runs (an earlier check-then-write version lost that race: 3861 of 20000 project-scope creates with `.tether` flipped between two symlinks, one into the catalog, wrote there): on Linux the destination directory is opened once, judged by its identity and its ancestors', and the file is written relative to it without following a symlink; an agent file that is itself a symlink is not written through while protected paths are in force, and the tool answers with a typed `agent_file_is_symlink` error ("edit the link's target, or replace the link with a regular file"), not an internal error; a symlinked directory that does not lead into a protected one is followed as before. Workers keep the `catalog.write` scope, which also gates the unprotected `scope=project`.
  - **Advisory against a hostile worker until caller identity lands (CW-20260930-0253):** any process that can reach `muxd.sock` can call `POST /sessions` with `agent_inline`, `injection` and an MCP list, so this and #85 close what that route reaches for the agents Tether wraps today without authenticating it, and neither covers Codex.
  - **Not yet covered:** `connect(2)` to the socket; writes delegated to same-uid services; the user and project definition layers (CW-20261001-0192); and `mux boot-exec`. See SECURITY.md. (CW-20261001-0142)
- **Client-visible:** `POST /sessions/{id}/input` and `/turn` answer a lost provider resume id with the new `provider_session_lost` error code instead of `conflict`. The HTTP status stays 409, so status-only clients are unaffected, and the MCP `mux_session_send_input`/`mux_session_send_turn` tools report the same code. Callers that branched on `conflict` for this case should match the new code.
- Dependency refreshes: `agentkit` v0.8.0, `go-providers` v0.29.0, `go-messaging` v0.5.2.
- Planning history and design-dead docs were archived out of the repository tree.

### Fixed

- **The `config.toml` planted into a codex boot dir states the launch's posture.** (CW-20261001-0216) It said `approval_policy = "never"`, the go-providers adapter's headless default, while the launch's argv carried `-c approval_policy="on-request"`. The argv is what runs, so nothing misbehaved, but a codex started from the boot dir without the argv would have run under `never`, which makes codex refuse every MCP tool call. The planted file now has `approval_policy = "on-request"` and `sandbox_mode = "workspace-write"` for both codex runtimes in both permission modes, taken from the same registry mapping that builds the argv.
- **Security: a Tether-launched Claude agent loads only the MCP servers Tether plants, and its proxy reaches only the upstreams it was granted.** (CW-20261001-0227)
  - Claude Code also loads servers from the operator's `~/.claude.json`, project `.mcp.json` files and the claude.ai connectors on the logged-in account. Every Claude launch now passes `--strict-mcp-config` (streaming, subprocess, pty, and resume), so only the planted `mux` proxy loads. That includes the claude.ai account connectors, which a launched agent no longer has. The kill switch is `TETHER_CLAUDE_STRICT_MCP=0` in muxd's environment. It logs a startup WARN, is reported in `/health` as `hardening`, and makes `mux doctor` warn (`claude-strict-mcp`); doctor reports the daemon's status, not its own environment. This is an interim flag until go-agent-wrapper has an option for it. `mux boot` is not covered: it runs the operator's own Claude with their own servers.
  - A launched agent's `mux mcp --proxy` is now confined (`--confine`) to an allow-list, by default `torque` and `tesseract`. Before, `--servers`/`MUX_MCP_SERVERS` only chose which upstream tools were listed natively: every upstream was still started, and `mux_discover`/`mux_call` still reached all of them, so every agent could call cerberus, loom and the rest. Now an upstream outside the list is never started, never resolved (its secrets are not read into the agent's proxy), and not reachable through `mux_call`/`mux_discover`. mux's own native tools are unaffected.
  - To grant more, list the upstreams in `mcp.servers` on the project, or `mcp_servers` in a boot profile. A non-empty list **replaces** the default, so name `torque` and `tesseract` in it too. A project that already lists upstreams keeps its list as written; the default applies only where none is set. `cerberus` is never in the default.
  - This is not a boundary against a hostile agent: agents run as the operator's uid and can still widen their own list through the API until CW-20260930-0253 (per-caller identity) and CW-20260930-0237 land. See SECURITY.md.
- **Security: an agent naming a sandbox profile the catalog doesn't define is refused at launch, and no longer stops the daemon.** Before, such an agent failed catalog validation, so the daemon refused to start at all. Separately, `LaunchSession`'s own lookup silently skipped an unknown `permissions.default_sandbox`, so a catalog that reached it unvalidated ran the session with no sandbox and no warning. Now the launch path fails closed on its own: creating, launching or resuming a session of that agent fails with **404 `not_found`** naming the agent and the missing profile, and an `agent_file`/`agent_inline` override that names one is refused at create. Startup no longer fails for one such agent. The daemon logs a warning, `ValidateLaunch` refuses that agent's launches, and `mux doctor` has a new `catalog-sandbox-profiles` check. An empty `default_sandbox` still means no sandbox. (CW-20261001-0130)
- **Security: an `agent_file`/`agent_inline` override's sandbox profile is applied at launch, and may not loosen a pinned one.** Session create merged an override's `permissions.default_sandbox` into the effective agent, but `LaunchSession` read the base catalog agent's profile. So an override asking for a stricter sandbox was silently dropped, and the session ran with the catalog agent's profile, or none. The plan now records an override's profile (`sandbox_profile`, only when it differs from the catalog agent's). `LaunchSession` applies it, or refuses if the catalog doesn't define it (404). **Interim rule until per-caller identity (CW-20260930-0253):** an override may name any profile for a catalog agent that has none, but only the same profile for a pinned agent. Anything else is refused with **403 `forbidden`**, because an agent holding `session.write` could otherwise loosen its own sandbox through a child session. Sessions without an override, and plans created before this field, keep using the catalog agent's profile. (CW-20261001-0145)
- **The MCP proxy no longer drops a strict stateless http upstream whose ping it can't satisfy.** go-sdk v1.8.0's client sends ping without the per-request `_meta` that a stateless go-sdk server on protocol 2026-07-28 requires, so the server answers -32602. The proxy treated that as unreachable and dropped the upstream's tools; tangent hit this until it pinned its protocol versions. go-mcp v0.14.1 counts a JSON-RPC error reply to ping as reachable, in the handshake and the health probe. Transport failures and 429/502/503/504 still fail. Bumps go-mcp v0.7.0 → v0.14.1, with no other behavior change for Tether. (CW-20261001-0078)
- **An actor is no longer left bound to a session that has ended.** Two sessions for one logical agent hold stacked binding generations. Stopping the newer one revoked its binding and promoted the older generation, even when that session had already ended, so mail to the agent was stored and never woken. A daemon restart did the same for every session its sweep marked `failed`. Now a session's bindings are revoked when it ends (stop, natural exit or crash). Daemon startup revokes the bindings of every ended Tether session, which also clears bindings orphaned before this release; bridge bindings are untouched. A superseded generation whose session is still running still becomes current again. **Client-visible:** `POST /messages/notify` to an agent whose binding names a session that is not running now answers `wake_reason: "session-not-running"` instead of a bare `wake_attempted: false`. (CW-20260912-0134)
- **A wake whose turn was submitted no longer lapses into retry before the agent reads its message.** `POST /messages/notify` (and the wake sweep) acked a wake to `turn_submitted` and left its 30-second lease for the recipient's consumption to close. An agent's turn takes longer than that, so every successful wake went to `retry_scheduled` with "lease expired", even after the agent had read and answered the message. The agent-os smoke run hit this with a message pulled through `mux_message_inbox`, which never settled a delivery. A submitted wake now holds its lease, still at `turn_submitted` (submission is not consumption), for up to 15 minutes. The recipient's consumption closes it as `delivered`. A wake that is never consumed lapses into one retry, which wakes the recipient again as a reminder. `GET /messages/inbox` takes `as_session`: when that live session is the recipient itself, the pulled messages are consumed, and `mux_message_inbox` passes its own session. An operator listing someone else's inbox still settles nothing. A retry that finds the message already consumed or read settles it without waking again; this covers a consume during a busy/offline backoff, when the delivery core refuses the claim. Busy, offline and failed-submit wakes still retry as before. (CW-20261001-0016)
- **Client-visible: a stopped session ends in `killed`, not `completed`.** `POST /sessions/{id}/stop` (and `mux sessions stop`, the MCP `mux_session_stop` tool and ACP session close, which all route through it) recorded the session as `completed`, with whatever exit code the process returned on the way down: `-1` when a signal ended it, and `0` when it exited cleanly on `SIGTERM` (the agent-os smoke run saw `completed`/`0` for a session hung on stdin). A host could not tell a cancel from an agent that finished without a result. The session row, `GET /sessions/{id}`, `mux sessions get` and the terminal `session.state_changed` event now say `killed`, the terminal state the API already documented but never wrote. The exit code is unchanged and still the process's own, so branch on `state`. Sessions that end on their own stay `completed` (exit 0) or `failed`, and the daemon-restart sweep still records `failed` with exit `-1`. Clients that treated `completed` as "ended" should add `killed`; `state` is a plain string in the Go client, so no client release is needed. (CW-20260930-0250)
- **A2A relay tasks survive a daemon restart, and a task a restart cut off is failed rather than left 'working'.** The inbound A2A relay used the A2A SDK's in-memory task store, so every delegated task an external peer had been told about disappeared on restart (`tasks/get` → not found). Task records now persist per binding in the new `a2a_tasks` table (migration 0032), so `tasks/get` answers after a restart and one binding still cannot read another's tasks. The wait a delegated task blocks on is process-local and cannot be persisted, so on startup any task left in `submitted` or `working` is moved to `failed` with a message saying the restart interrupted it; the relayed message itself is unaffected and the peer resubmits. Settled tasks, including `input-required` ones, are left as they were. (CW-20260930-0063)
- **`mux daemon stop` no longer signals a process it has not identified as muxd.** The pidfile is removed only on graceful shutdown, so after a crash it can name a PID the OS has since handed to an unrelated process, and `stop` sent `SIGTERM` to whatever held the number. `stop` now reads the PID's command line (via `go-localdaemon`'s `VerifyCommand`) and signals only a `mux daemon run` process; a live PID that is not muxd is reported and the stale pidfile removed, and a check that cannot be made refuses to signal. The start guards (`daemon start`, `daemon run`, the server's own pre-flight and `WritePIDFile`) and `daemon status` apply the same identity check, so a recycled PID no longer makes start refuse or status report a live daemon; when identity cannot be checked they still err toward "already running". Adds a dependency on `go-localdaemon` v0.1.0. (CW-20260930-0045)
- Catalog reload failures are redacted in MCP output, and launch catalog reads refresh correctly.
- Six registry re-onboarding and group-props bugs found in review.
- The messaging pull-only fencing gap, a binding-lease TOCTOU race, and a late-Nack-reverses-Consume race.

## [0.6.0] - 2026-09-11

### Added

- Group messaging, the federation directory (registry) and authority-routing peer configuration for messaging.
- An AI gateway runtime with streaming chat events over MCP, Gemini/embeddings/multimodal shorthands, an Ollama-compatible fallback, and OpenAI key setup through the keychain.
- OpenTelemetry propagation and AI spans; adoption of `agentkit` v0.2.0 for the runtime.
- Curated MCP proxy discovery, a notify wake path for messages, and Task-bundle planting for Codex worktrees.
- Sysop UI served at the site root with Operations as the home view.

### Changed

- Storage paths fall back to `go-apppaths`; release-readiness hardening of install and Sysop UI build paths.

## [0.3.0] - 2026-05-14

### Added

- Three-layer catalog discovery with schema extensions, a skills package with Claude and Codex compilers, and `mux agents create|edit|show`.
- A caller-provided launch surface and session-mutating MCP tools routed through the daemon.
- An ACP server (`mux acp`) bridging to the session service.

### Fixed

- Boot-command namespace collision; `acpsvc` infinite loop on attach error.

## [0.2.1] - 2026-05-09

### Fixed

- Patch release over v0.2.0; see `git log v0.2.0..v0.2.1` for detail.

## [0.2.0] - 2026-04-27

### Added

- Codex CLI support (boot, launch); ephemeral temp-dir model for Claude sessions; selective flat MCP proxy with a `--servers` filter (`--broker` deprecated).
- Message routing contract and durable messaging store with `/messages/*` HTTP routes; event durability and an observation query surface; a provider compliance suite and capability matrix.
- Sandbox profile registry integrated with the catalog; checkpoint/resume with logical-agent resume.
- `mux_discover` returns `totalMatches` so callers can detect truncation.

### Fixed

- MCP event forwarder and proxy-polling bugs; `mux_message_inbox` kind filter description aligned with the valid enum.

## [0.1.0] - 2026-04-21

### Added

- Initial release: the `muxd` daemon with session lifecycle, PTY/process management, an attach broker with ring-buffer fan-out and `since_seq` resume, session lifecycle events, an API/stub runtime, launch resolution with boot-prompt composition, the `mux` CLI, and golangci-lint-gated quality checks.
