# Changelog

All notable changes to Tether are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Pre-1.0: minor bumps for additive surface, patch bumps for fixes — breaking changes can land in any minor.

This file was backfilled from the git history and is a good-faith summary, not an exhaustive one; `git log` is the complete record. Entries are grouped by tagged release. Consumers should watch this file for new HTTP routes, MCP tools, CLI commands and catalog/configuration changes.

- The fail-closed protection path no longer takes everything with it, and five holes the review of #149 found are closed (CW-20261003-0096; all pre-existing in b01e3ec). (1) A project whose `repo_root` is missing under an unwritable directory that the daemon's user owns, or can move aside (realistically an unmounted mountpoint inside the home, such as `~/mnt/nas`), refused EVERY protected launch (403), made a Codex launch answer create 201 and then launch 500, and made the daemon MCP runtime fail to build (`NewSharedUpstreams` via `DaemonProtectedRoots.paths()`: every new `/mcp` view failed after a restart, taking out the `mcp__tether__*` gateway). Now that directory is anchored read-only (inside the sandbox `chmod` and `mkdir` are `EROFS`, and neither it nor any directory above it can be renamed: `EBUSY`), nothing is refused, and `GET /health` lists it under `sandbox_protect.anchored_project_ancestors` with a doctor warning; the launch that would work inside it is refused like one inside any anchor. A project whose layer still cannot be protected (a file in the way under a writable directory, a symlink an agent can replace, an unexaminable root, a planted layer) is refused with its own code, `403 project_layer_unprotectable`, naming the project, not the generic `forbidden` that read as missing bubblewrap. The daemon's MCP gateway and the planted proxy of a Codex launch are NOT refused for another project's broken entry: that layer is left out of their confinement and reported (`WARN ... LEFT OPEN`), so a broken project entry does not take out the gateway or an unprotected Codex launch for the shapes handled here (it still does for a `<root>/.tether` that is a file and for a root under a file: known limits below); the launching project's own missing root is the typed `409 project_root_missing` for Codex too. (2) The placeholder's `.tether` is made with `mkdir` and checked: a layer that turned up first, or got content while Tether made it, was anchored and reported as a clean created root with the planted file in it (reproduced with a racing thread); it is now refused with a typed error. (3) A placeholder is keyed on its marker `.tether/created-by-tether-protection` alone, no longer on the root holding nothing else: one file dropped into the root turned the launching project's typed 409 into a 201 and emptied `created_project_roots`. Restoring the repository is removing the marker. (4) A `repo_root` that runs through a symlink an agent can replace (unlink it, put a real directory with a planted layer where it was; reproduced for a dangling link whose target chain is root-owned, which was skipped) is refused, naming the link; the wording "nothing the agent can do creates the root" is true only without such a link. (5) A project root under a file made the daemon refuse to start (the layered loader read `.tether/agents` and got `ENOTDIR`); a layer directory that cannot be there because something above it is a file is now a missing layer (the gateway's own catalog cache still answers `/mcp` 503 for that shape: known limit below). A root that cannot be examined (`EACCES`, a loop) is a typed refusal, not a bare 500, and a name too long to exist (`ENAMETOOLONG`) is skipped, but only in unit tests: a running daemon refuses to start for such a root before protection runs. A strict call now names EVERY project it cannot protect, and `GET /health` lists them in `sandbox_protect.unprotectable_project_layers` with why and the fix (for a symlink: replace it with the real directory, or fix `repo_root`). **Known limits, not handled and none reachable on the live catalog (CW-20261003-0106; see "Known limits" in docs/sandboxing.md):** a `<root>/.tether` that is a file (an untyped 500 on every protected launch, Codex create 201 then launch 500, `/mcp` 503); a root under a file (`/mcp` 503); `ENAMETOOLONG`/`EACCES`/loop roots are reachable only in unit tests; the placeholder-race refusal is one-shot (the next call adopts what the racer planted); a symlinked layer (`<root>/.tether` or `.tether/agents` as a symlink) is not covered; a user-owned unwritable `/` as the nearest ancestor is an untyped 500; and a project added while the daemon runs is not in the protection snapshot until the next restart.

- Protection no longer skips a missing project root on the strength of "the nearest directory is not writable" (CW-20261003-0093, delta review of CW-20261003-0092): the agent runs as the daemon's user, so a read-only directory that user owns can be `chmod`ed writable, and a directory can be renamed aside through a writable parent (`mv ro ro-old; mkdir ro`), after which the agent planted a `.tether` layer that the next catalog load read; the owned case is reproduced for real under bubblewrap. A root is now skipped only when no directory from its nearest existing ancestor up to `/` is owned by the daemon's user or writable by it (a sticky directory counts only for what the user owns); where the agent can get past an unwritable ancestor, that ancestor is anchored read-only (CW-20261003-0096; this entry first refused the launch, 403 with `plan_error` in `GET /health`, which refused every protected launch). No live project is affected: all 7 dead roots sit under writable user-owned directories and are anchored as before.

- Protected launches survive catalog projects with a missing `repo_root` (CW-20261003-0092): one registered project whose `repo_root` did not exist made every launch Tether must protect (Claude, OpenCode, every agent it wraps) fail at create with `500 internal_error` `protect catalog layer: parent unavailable`, since the layered-catalog protection landed (CW-20261001-0539). Skipping such a project would have left it open (the sandbox base is the whole host, writable, so an agent can create the missing root and a `.tether` layer in it, and the next catalog load reads it), so instead: where an agent could create the root (the nearest existing directory above it is writable by the daemon's user, tested with `access(2)`), the root is created as a placeholder holding only a `.tether` (0700, with a one-file `created-by-tether-protection` note the catalog loader ignores) and that layer is anchored read-only like any other (`sandbox_protect.created_project_roots` in `GET /health`, one warning per project, a `tether doctor` warning; the report survives a restart because the note tells a placeholder from an empty project directory); where it could not, the layer is skipped and reported (`skipped_project_layers`); a file in the way under a writable directory refuses the launch; the launching project's own missing root, or a root that is only the placeholder made for it, is `409 project_root_missing` naming the project and path, and a launch never creates its own project's root. Every root is decided before any directory is created, so a refused launch leaves nothing behind. `/health` no longer blames bubblewrap for a catalog problem: `plan_error` carries the real reason and the bubblewrap probe stays its own answer. Existing project layers are protected exactly as before.

- Upstream conformance (CW-20260926-0011): report-only input-schema syntax/local-reference checks, explicit unexamined external/oversized schemas, and origin-scoped observed initialization instructions over 2,048 characters through gateway status and live doctor. Schema lint is memoized outside locks with per-tool and aggregate budgets, explicit unexamined counts, and no remote fetch or metadata changes; upstream-author guidance links Tangent's separate rename task CW-20261001-0646.

Each new launch preflights the strict opt-in MCP endpoint and fails with a fix hint if unavailable. Claude/OpenCode/Codex consumed configs retain their control-plane protection, upstream environment is excluded from the worker, and doctor reports ownership/identity plus captured active-session counts. Selector changes affect new launches only; existing proxies require deliberate drain/relaunch. Idle forwarders recover before tool dispatch; every tool call is sent once. Interrupted SSE streams may resume by GET with Last-Event-ID (the retry bound counts consecutive resumes without progress), without re-posting tools/call. Session replacement preserves admitted calls and does not block other callers on SDK teardown; synthetic lost-response errors are typed daemon_unreachable. No live cutover or enforcement change.
- Daemon MCP endpoints (CW-20261001-0539, stage 2): opt-in `daemon.mcp_endpoint.enabled: true` (default false) mounts `/mcp` and `/p/<profile>` over TCP/UDS. Strict bearer admission applies in observe mode; credential/policy-bound SDK sessions enforce profile floors and Origin/Host checks. Only admitted origins start under mandatory confinement, with no global handshake lock. Per-principal quotas/operator headroom prevent one credential consuming all views. Revocation cancels streams and in-flight calls (outcome may be unknown); transient verifier/catalog errors retain sessions but refuse calls until verification recovers. Generation caching avoids reparsing unchanged catalogs. Shutdown drains calls up to the configured timeout before closing the pool/store. Typed collisions preserve healthy origins and refresh recovery; initialization omits daemon PID. Doctor and the seeded catalog show the opt-in; disabled daemons retain existing behavior. Enablement is 0230's optional phase-2 rollout, separate from live cutover. Existing stdio forwarders remain until later cutover; no deployment is performed.
- Gateway metadata diagnostics (CW-20260926-0010): gateway status counts profile exclusions by reason and reports per-origin eligible/available inventory. Unavailable upstream health reports zero current `tool_count`, preserves accepted `cataloged_tools`, and distinguishes unexamined inventory from an observed empty list. Status and opt-in live doctor share report-only warnings for missing annotations, descriptions over 2,048 characters, and listed tools described as Disabled. An eligible named status lookup includes its origin and verbatim authored annotations; no safety labels or availability are guessed from prose.

- Trusted HTTP/SSE forwarding (CW-20261001-0543, part B): daemon-owned upstream entries can provision a dedicated upstream-issued proxy service bearer through an explicit `proxy_service_token_file` (absolute path, owner/regular/0600/no-symlink checks). Initialization, probes and stream GETs carry service authentication without actor headers; service-authenticated SSE streams survive the handshake deadline until SDK body closure. Service secrets stay out of worker delivery and are scrubbed from successful and failed tool results as well as errors. No new table/migration or live rollout; upstream service-principal provisioning and receiver trust remain operator-owned.

- Daemon MCP foundation (CW-20261001-0539, stage 1): one shared upstream owner with credential-bound, profile-aware SDK views; mandatory protect-only confinement for its stdio children, visible remote exclusion unless `allow_unconfined_remote`, and operator-provisioned `identity.mcp_grants` for service/interactive principals. HTTP/UDS mounting and production forwarder cutover follow in later stages; today's stdio proxy remains active. Per-agent sandboxes do not cover daemon-owned upstreams, so per-app confinement remains necessary. Same-uid operator-token theft remains possible until CW-20260930-0237; upstreams still attribute calls to their shared catalog credentials.

- Trusted MCP call attribution (CW-20261001-0543, part A): `GET /auth/context` resolves secret-free session/agent/workstream/launch context from the daemon-verified principal. Observe/off calls remain available. HTTP forwarded-user headers and service-credential provisioning follow in part B; no deployment or enforcement change.

- **Terminal A2A task retention.** The hourly `daemon.events_retention` sweep now expires completed, failed, canceled and rejected relay tasks whose last update is older than the shared window (default 90 days). Non-terminal tasks never expire; disabling retention preserves all tasks. Deletions have atomic durable audit receipts. Expired tasks are no longer available through peer lookup. (CW-20260930-0249)

- Caller identity phase 1 client/session plumbing (CW-20260930-0253): CLI/MCP lookup prefers `--token-file`, `TETHER_TOKEN`, then the selected catalog's operator file; session/anonymous boot proxies never use that fallback. Launch/resume mints a scoped session credential in ENV, with verified creator inheritance, a seven-day expiry backstop and no token in argv/stored plans. Created-session retries atomically replace stale tokens. Migration 0037 backfills duplicate/terminal credentials and revokes tokens transactionally at terminal/delete states; failed launches revoke only their own token. Observe mint failures continue anonymously; per-session preparation preserves concurrent winners. Stdio upstreams inherit no `TETHER_*TOKEN` credential unless their catalog explicitly supplies it. Existing sessions require relaunch; observe remains default and cutover ownership is unchanged.

- **Durable manual message-body purge receipts.** Every actual purge commits a `message_purge_audit` row (table, message ID, `authorized_by` and time) with the content removal. Failed audit writes preserve the body, and idempotent retries add no receipt. Authorization remains a self-asserted URN. Legacy `broker_envelopes` remains indefinitely and is explicitly outside this messages-only purge path. (CW-20260930-0010)

- **Verified caller identity core (CW-20260930-0253, phase 1 A).** Token rows store hashes and a stable principal id; daemon bootstrap creates an exclusive 0600 operator file. Default `observe` verifies supplied credentials without rejecting requests, with a bounded asynchronous audit queue and drop/failure counters in health/doctor. Anonymous requests do no audit work, and no per-request event wakes event waiters. Audit rows share the default 90-day retention sweep and durable purge receipts. Operator-file/DB mismatches warn and degrade observe startup; only explicit `enforce` fails closed. Mode/listener validation applies at daemon startup, with doctor findings; A2A remains under its own authentication. Route scopes and address policy remain phase 2. No live enforcement or restart is performed; back up/restore the matching DB and token-file pair, and see `docs/caller-identity.md`.

- **An MCP server catalog entry can take a credential from a private file.** (CW-20261001-0229) `file:///abs/path` or `file://~/path` in `args:`, `env:`, `token:` or `url:` is read at spawn time, so the catalog YAML no longer has to carry the secret. The file must be a regular file owned by the current user with mode 0600 or tighter (a group- or world-readable file is refused), and a symlink must stay inside the catalog directory or the operator's home. A missing, empty or oversized file, or one that is not a regular file (a FIFO is refused before it is opened, so it cannot hang the load), fails the load with an error that names the file and never contains its contents. The value is redacted from an upstream's stderr tail, tool-call errors, launch records and the connect errors in a server's status and the log, like a keychain value, and a `url:` that came from a reference is scrubbed too. Only a `file://` the catalog YAML wrote is a reference: a value that becomes `file://` through `${VAR}` stays a literal, and `${VAR}` is not expanded inside a `file://` path (`~` still follows `$HOME`, which a launch's environment can set, so use an absolute path to pin the file). Put the reference in `env:` to keep it off the command line; in `args:` the value is still on the upstream's `/proc/<pid>/cmdline`, and `tesseract mcp` and `hadrond mcp` currently take their token only as `--token`. A literal MCP-entry value written as `file://` is read as a credential file, so one that is not fails the load; none exists in the live catalog. See `docs/secrets.md`.
- **Events retention sweep.** `daemon.events_retention` runs an hourly age-based sweep of `events`, `proxy_events` and `ai_events` in bounded batches, using the daemon's shared periodic-job loop. It defaults to 90 days enabled; see Changed below for the existing-install deletion warning and disable controls. (CW-20260930-0008, CW-20261001-0545)
- **Idempotent session create and resume.** `POST /sessions` and `POST /logical-agents/{id}/resume` accept an optional `idempotency_key`: a retry with the same key and request returns the session the first one created (`replayed: true`, HTTP 200), and the same key with a different request answers 409 `idempotency_conflict`. Launching a keyed session again is idempotent too. Keys are global and unauthenticated, so prefix them. Surfaced in the Go client (`ResumeLogicalAgentWithOptions`), the MCP `tether_session_create` / `tether_logical_agent_resume` tools, and `tether launch --idempotency-key` (CW-20260930-0229).
- **Messaging surfaces.** Scoped role/slot binding across CLI, MCP, HTTP and the Go client; a durable participant registry with canonical sessions and leased runtime bindings; durable hosted-session handoff with route fencing; delivery trace, operator repair and privacy-safe retention; and a bounded, server-only inbound A2A relay adapter.
- **MCP adapter: streamable-HTTP transport**, so an upstream restart no longer severs connected agents. Upstream `sse`/`http` connections and supervision now use the shared `go-mcp` client and supervisor packages.
- **Registry: derived/authored field split on project entries**, callback-backed derivation, an onboarding/lookup surface, flat authored `props`, and minter/owner provenance with symmetric redaction on write routes.
- **Launch profiles.** `config.Agent` is now `LaunchProfile`, with compositional launch resolution and a Global > Project > User settings cascade for onboarding configuration.
- **Runtimes.** An `opencode` runtime on the structured go-providers adapter (with resume verification and a skills compiler) and an Antigravity (`agy`) runtime with detect/seed/doctor support and provider events.
- **MCP proxy:** typed identifier extraction from proxied calls into session refs, and bounded workstream provenance on forwarded calls.

- An inert team service centralizes formation, membership, messaging, cancellation and result reporting behind authenticated principal and host-policy ports. Caller-scoped durable receipts retain selected recipients and completed results across retries; mesh team operations enforce grants and spawn limits. No daemon routes or runtime wiring are enabled.

- Add default-off HTTP, MCP and CLI team verb wrappers over the authenticated team service, with per-verb field and required-input validation, shared request/result contracts, caller-scoped keys and cause-free error codes. All nine MCP verbs require the new `team.write` scope. Disabled team routes and tools are absent, and CLI verbs are undiscoverable. Host activation remains separate.

### Changed

- **MCP names are explicit and collision-safe** (CW-20260926-0009): catalog `tool_prefix` prepends exactly the declared value and preserves the upstream call name; final-name collisions (including gateway names) fail startup instead of creating arrival-order aliases. A colliding refresh/reconnect retains accepted schemas and reports degraded status. Catalog origin `tether` is reserved; naming checks do not block generic catalog/daemon commands. Gateway status reports portable-name, origin and client-qualified length lint without rewriting names. Default doctor checks declarations offline; `doctor --mcp-live` explicitly spawns upstreams for a bounded tools/list-only probe with credential/URL-redacted findings.

- **Named MCP gateway profiles** (CW-20260926-0008): `--profile` / `TETHER_MCP_PROFILE` select origin-based filters, final-name allow/deny globs, advisory read-only filtering, pinned/server/name ordering, eligible alwaysLoad hints and bounded instructions. Profiles apply before ranking and across listing, hydration and dispatch; unknown selectors/origins fail; unknown pins fail when discovery is complete and warn while an upstream is unavailable. Flat ordering intentionally changes from alphabetical to native origins first, then catalog server order, then final name (ADR 0047), even without a profile. Native origin `tether` is explicit in a server list; gateway infrastructure remains visible.

- **MCP grants fail loudly.** Daemon startup and affected launch/session chains reject unknown or disabled upstream IDs; doctor names the owner and bad grant. Explicit empty project/launch `mcp.servers`, boot-profile `mcp_servers`, and environment grants now mean no upstreams; omitted/null lists still inherit. Native Tether tools remain available. (CW-20261001-0443)
- **Selectable MCP discovery mode** (CW-20261001-0542): flat remains the default with no discovery/dispatch hatch; explicit search exposes `tether_tool_search`, `tether_tool_list`, `tether_tool_call` and `tether_gateway_status`. Argument/env/config/persisted settings select the mode, with every supplied value validated. List supports enumeration and exact schema hydration, search supports summary/schema detail, and cursors reject changed inventories. `--servers` restricts loading and every call path; unknown/disabled IDs fail, and `--broker` is removed. Profile selection follows separately.

- **Retention is on by default for 90 days.** `daemon.events_retention` now governs `events`, `proxy_events` and `ai_events` by age; proxy/AI inserts no longer evict rows above 2,000. Set `days` below 1 or `enabled: false` to disable. **On existing installs the first sweep deletes old rows unless explicitly disabled; back up the state database before cutover.** Every deletion batch writes an atomic durable audit receipt, and the sweep exposes per-table counts for future consumers. The API reference lists lifecycle tables retained outside this policy; archiving remains out of scope. (CW-20261001-0545)
- CW-20260926-0007: clean break from mux to tether (CLI, MCP tool/server names, environment and socket paths); no compatibility aliases. Durable identity authorities and historical SQL are retained.

- **Library bump: go-agent-wrapper v0.25.6, agentkit v0.21.0, go-providers v0.42.0, go-sandbox v0.6.0, go-runner v0.8.2, go-llm-contracts v0.4.0** (go-llm-types stays at v0.5.1). (CW-20261001-0210) Every first-turn argv, and every other runtime's argv, is byte-identical to before, because Tether launches through the prepared launch template and agentkit v0.21.0 changes only the path without one. The one argv that changes is a codex exec turn that resumes a thread, which gains `resume <id>` (first bullet below). What changes, as measured on a live daemon with the real codex-cli 0.159.3:
  - **A codex exec session resumes its thread from turn 2.** Within one session, turn 2 runs `exec … --cd <project> resume <id> -- <prompt>`, with every exec option in front of `resume`, in the same `CODEX_HOME`, and both turns end up in one codex thread (one rollout file holding both prompts). Before, every turn started a new thread.
  - **A logical-agent resume of a codex agent starts a fresh thread.** It is a new session with a new boot dir and so a new `CODEX_HOME`, and the checkpoint Tether writes carries no provider session id (`provider_hints_json` is empty), so the first turn has no `resume`; that session then resumes its own thread from its second turn. Nothing carries a codex thread across boots.
  - **If a checkpoint's provider hints ever do carry a thread id,** resuming into a `CODEX_HOME` that lacks it fails that one turn as a provider session loss, not as a launch failure and not as a 502: the turn returns `provider_session_lost` (HTTP 409), the session log records `[session_lost] requested=<id>` and codex's own `no rollout found for thread id` line, and the next turn starts a fresh thread. Nothing in Tether writes such hints today. No `provider.session_lost` event is published for this case: the lib reports it through the session log marker, and Tether's event covers a turn that ran on in a new session.
  - A per-turn resume that fails because the provider no longer has the session now leaves a `[session_lost]` marker in the subprocess session log, for an adapter that classifies the loss (agentkit v0.20.2). Measured here for codex exec; I did not exercise the Claude or OpenCode adapters.
- **The `tether mcp` server Tether plants in each agent no longer opens the state database.** It runs inside the agent's sandbox and used to open `tether.db` read-write in-process (migrations, the logical-agent seed, and the proxy's tool-call events), which is why the state directory could not be protected. Launched sessions now get `tether mcp --daemon-only`: it reads and writes Tether state only through the daemon's API, the daemon records each tool call itself, and it refuses to start without a reachable daemon (`tether daemon unreachable; tether tools unavailable`). An agent launched while `tetherd` is down has no tether tools. An operator's own `tether mcp` and `tether boot-exec` are unchanged. (CW-20261001-0173)
  - **Client-visible:** `POST /proxy/events` accepts optional `phase` (`start` or `end`) and `publish`. With `publish` the daemon publishes the call on its event bus, and a non-empty `session_id` must name an existing session (400 otherwise). It checks shape and size (400 on a malformed record or a body over 64 KiB; an over-long `error` is cut to 4 KiB with a `…[truncated]` marker). **For every caller, published or not, the daemon now stamps the time itself and ignores `timestamp`.** `GET /sessions/{id}` gains `workstream_id`.
  - **Inside an agent**, `tether_session_health` and `attached_clients` now come from the daemon (before, the planted server asked its own empty session manager), and `tether_logical_agent_list` returns the daemon's summary rather than the table row, with different JSON keys (`id`, `name`, … rather than `ID`, `Role`, …). An agent launched while `tetherd` is down has no proxied upstream tools either, not only no native tools.
- **Permission modes reach each provider as a posture, with no change to what an agent may do.** go-agent-wrapper v0.23.0 (agentkit v0.19.1, go-providers v0.39.0, go-sandbox v0.5.1) takes a launch's permission as a go-permission posture and refuses a provider's own spelling. Tether now maps `permission_mode` onto one posture per provider, the same in both launch engines:
  - claude: `bypass` runs with `--permission-mode bypassPermissions` instead of `--dangerously-skip-permissions`, and `default` runs with `--permission-mode default`.
  - codex: runs `workspace-write` with `approval_policy` `on-request` in both modes, as before. That is the policy under which its MCP tool calls are asked for and approved, rather than refused.
  - opencode: keeps its own defaults.
  - antigravity: `bypass` passes `--dangerously-skip-permissions`, and `default` passes `--mode accept-edits`.

### Fixed

- **The `config.toml` planted into a codex boot dir states the launch's posture.** (CW-20261001-0216) It said `approval_policy = "never"`, the go-providers adapter's headless default, while the launch's argv carried `-c approval_policy="on-request"`. The argv is what runs, so nothing misbehaved, but a codex started from the boot dir without the argv would have run under `never`, which makes codex refuse every MCP tool call. The planted file now has `approval_policy = "on-request"` and `sandbox_mode = "workspace-write"` for both codex runtimes in both permission modes, taken from the same registry mapping that builds the argv.
- **Security: a Tether-launched Claude agent loads only the MCP servers Tether plants, and its proxy reaches only the upstreams it was granted.** (CW-20261001-0227)
  - Claude Code also loads servers from the operator's `~/.claude.json`, project `.mcp.json` files and the claude.ai connectors on the logged-in account. Every Claude launch now passes `--strict-mcp-config` (streaming, subprocess, pty, and resume), so only the planted `tether` proxy loads. That includes the claude.ai account connectors, which a launched agent no longer has. The kill switch is `TETHER_CLAUDE_STRICT_MCP=0` in tetherd's environment. It logs a startup WARN, is reported in `/health` as `hardening`, and makes `tether doctor` warn (`claude-strict-mcp`); doctor reports the daemon's status, not its own environment. This is an interim flag until go-agent-wrapper has an option for it. `tether boot` is not covered: it runs the operator's own Claude with their own servers.
  - A launched agent's `tether mcp --proxy` is now confined (`--confine`) to an allow-list, by default `torque` and `tesseract`. Before, `--servers`/`TETHER_MCP_SERVERS` only chose which upstream tools were listed natively: every upstream was still started, and `tether_tool_search`/`tether_tool_call` still reached all of them, so every agent could call cerberus, loom and the rest. Now an upstream outside the list is never started, never resolved (its secrets are not read into the agent's proxy), and not reachable through `tether_tool_call`/`tether_tool_search`. tether's own native tools are unaffected.
  - To grant more, list the upstreams in `mcp.servers` on the project, or `mcp_servers` in a boot profile. A non-empty list **replaces** the default, so name `torque` and `tesseract` in it too. A project that already lists upstreams keeps its list as written; the default applies only where none is set. `cerberus` is never in the default.
  - This is not a boundary against a hostile agent: agents run as the operator's uid and can still widen their own list through the API until CW-20260930-0253 (per-caller identity) and CW-20260930-0237 land. See SECURITY.md.
- **Security: an agent naming a sandbox profile the catalog doesn't define is refused at launch, and no longer stops the daemon.** Before, such an agent failed catalog validation, so the daemon refused to start at all. Separately, `LaunchSession`'s own lookup silently skipped an unknown `permissions.default_sandbox`, so a catalog that reached it unvalidated ran the session with no sandbox and no warning. Now the launch path fails closed on its own: creating, launching or resuming a session of that agent fails with **404 `not_found`** naming the agent and the missing profile, and an `agent_file`/`agent_inline` override that names one is refused at create. Startup no longer fails for one such agent. The daemon logs a warning, `ValidateLaunch` refuses that agent's launches, and `tether doctor` has a new `catalog-sandbox-profiles` check. An empty `default_sandbox` still means no sandbox. (CW-20261001-0130)
- **Security: an `agent_file`/`agent_inline` override's sandbox profile is applied at launch, and may not loosen a pinned one.** Session create merged an override's `permissions.default_sandbox` into the effective agent, but `LaunchSession` read the base catalog agent's profile. So an override asking for a stricter sandbox was silently dropped, and the session ran with the catalog agent's profile, or none. The plan now records an override's profile (`sandbox_profile`, only when it differs from the catalog agent's). `LaunchSession` applies it, or refuses if the catalog doesn't define it (404). **Interim rule until per-caller identity (CW-20260930-0253):** an override may name any profile for a catalog agent that has none, but only the same profile for a pinned agent. Anything else is refused with **403 `forbidden`**, because an agent holding `session.write` could otherwise loosen its own sandbox through a child session. Sessions without an override, and plans created before this field, keep using the catalog agent's profile. (CW-20261001-0145)
- **The MCP proxy no longer drops a strict stateless http upstream whose ping it can't satisfy.** go-sdk v1.8.0's client sends ping without the per-request `_meta` that a stateless go-sdk server on protocol 2026-07-28 requires, so the server answers -32602. The proxy treated that as unreachable and dropped the upstream's tools; tangent hit this until it pinned its protocol versions. go-mcp v0.14.1 counts a JSON-RPC error reply to ping as reachable, in the handshake and the health probe. Transport failures and 429/502/503/504 still fail. Bumps go-mcp v0.7.0 → v0.14.1, with no other behavior change for Tether. (CW-20261001-0078)
- **An actor is no longer left bound to a session that has ended.** Two sessions for one logical agent hold stacked binding generations. Stopping the newer one revoked its binding and promoted the older generation, even when that session had already ended, so mail to the agent was stored and never woken. A daemon restart did the same for every session its sweep marked `failed`. Now a session's bindings are revoked when it ends (stop, natural exit or crash). Daemon startup revokes the bindings of every ended Tether session, which also clears bindings orphaned before this release; bridge bindings are untouched. A superseded generation whose session is still running still becomes current again. **Client-visible:** `POST /messages/notify` to an agent whose binding names a session that is not running now answers `wake_reason: "session-not-running"` instead of a bare `wake_attempted: false`. (CW-20260912-0134)
- **A wake whose turn was submitted no longer lapses into retry before the agent reads its message.** `POST /messages/notify` (and the wake sweep) acked a wake to `turn_submitted` and left its 30-second lease for the recipient's consumption to close. An agent's turn takes longer than that, so every successful wake went to `retry_scheduled` with "lease expired", even after the agent had read and answered the message. An earlier smoke run hit this with a message pulled through `tether_message_inbox`, which never settled a delivery. A submitted wake now holds its lease, still at `turn_submitted` (submission is not consumption), for up to 15 minutes. The recipient's consumption closes it as `delivered`. A wake that is never consumed lapses into one retry, which wakes the recipient again as a reminder. `GET /messages/inbox` takes `as_session`: when that live session is the recipient itself, the pulled messages are consumed, and `tether_message_inbox` passes its own session. An operator listing someone else's inbox still settles nothing. A retry that finds the message already consumed or read settles it without waking again; this covers a consume during a busy/offline backoff, when the delivery core refuses the claim. Busy, offline and failed-submit wakes still retry as before. (CW-20261001-0016)
- **Client-visible: a stopped session ends in `killed`, not `completed`.** `POST /sessions/{id}/stop` (and `tether sessions stop`, the MCP `tether_session_stop` tool and ACP session close, which all route through it) recorded the session as `completed`, with whatever exit code the process returned on the way down: `-1` when a signal ended it, and `0` when it exited cleanly on `SIGTERM` (an earlier smoke run saw `completed`/`0` for a session hung on stdin). A host could not tell a cancel from an agent that finished without a result. The session row, `GET /sessions/{id}`, `tether sessions get` and the terminal `session.state_changed` event now say `killed`, the terminal state the API already documented but never wrote. The exit code is unchanged and still the process's own, so branch on `state`. Sessions that end on their own stay `completed` (exit 0) or `failed`, and the daemon-restart sweep still records `failed` with exit `-1`. Clients that treated `completed` as "ended" should add `killed`; `state` is a plain string in the Go client, so no client release is needed. (CW-20260930-0250)
- **A2A relay tasks survive a daemon restart, and a task a restart cut off is failed rather than left 'working'.** The inbound A2A relay used the A2A SDK's in-memory task store, so every delegated task an external peer had been told about disappeared on restart (`tasks/get` → not found). Task records now persist per binding in the new `a2a_tasks` table (migration 0032), so `tasks/get` answers after a restart and one binding still cannot read another's tasks. The wait a delegated task blocks on is process-local and cannot be persisted, so on startup any task left in `submitted` or `working` is moved to `failed` with a message saying the restart interrupted it; the relayed message itself is unaffected and the peer resubmits. Settled tasks, including `input-required` ones, are left as they were. (CW-20260930-0063)
- **`tether daemon stop` no longer signals a process it has not identified as tetherd.** The pidfile is removed only on graceful shutdown, so after a crash it can name a PID the OS has since handed to an unrelated process, and `stop` sent `SIGTERM` to whatever held the number. `stop` now reads the PID's command line (via `go-localdaemon`'s `VerifyCommand`) and signals only a `tether daemon run` process; a live PID that is not tetherd is reported and the stale pidfile removed, and a check that cannot be made refuses to signal. The start guards (`daemon start`, `daemon run`, the server's own pre-flight and `WritePIDFile`) and `daemon status` apply the same identity check, so a recycled PID no longer makes start refuse or status report a live daemon; when identity cannot be checked they still err toward "already running". Adds a dependency on `go-localdaemon` v0.1.0. (CW-20260930-0045)
